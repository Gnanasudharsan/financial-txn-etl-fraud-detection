01 · The brief

Three problems every bank pays for, every single day.

The goal was to build what a payments data team actually runs, not a notebook demo. That means production structure, real failure modes, and numbers that can be checked.

Data arrives dirty

Nulls, duplicates, malformed amounts, impossible timestamps, corrupt lines and schema drift. The simulator injects defects across files ( GB), the same kinds real feeds have.

Fraud hides in volume

fraudulent transactions across five attack patterns (card testing, account takeover, velocity bursts, night-time spending, high-risk merchants), mixed in with legitimate look-alikes on purpose.

The books must balance

Every entry in the internal ledger has to match a processor settlement: against rows, with amount drift, timing gaps, duplicates and orphans to find.

Honest note The data is simulated, with seeded randomness and ground truth for every defect, fraud and break. That makes every claim on this page checkable, and it also means the fraud is easier to catch than in real life. Both points come up again below.

    Raw · simulator

    Simulate a bank, flaws and all

    A seeded, chunked generator builds 50k customers, 100k Luhn-valid cards and 20k merchants, then six months of transactions in CSV and JSON-lines. Fraud is injected as episodes, not random labels: a stolen card is tested with tiny charges, then drained. On top of that come the defects, a ledger, a settlement feed with deliberate breaks, and a ground-truth file for everything.

    • Faker
    • NumPy
    • seed 42
    • fits in 0.85 GB of RAM

    Bronze · land it exactly once

    Card numbers never touch the lake

    The moment a row lands, the card number becomes an HMAC-SHA256 token plus its last four digits, computed in native Spark SQL with no Python UDF. Ingestion is incremental and idempotent: a processed-file log and Delta's txnAppId/txnVersion, so a crash between two commits can't double-load. Corrupt lines and unexpected columns are kept for later, never silently dropped.

    • Delta Lake
    • PERMISSIVE parsing
    • _rescued_data
    • MERGE for dimensions

    Silver · trust, but verify

    Every rejected row says why

    Explicit schemas, four timestamp formats normalized to UTC, currencies converted to USD, and exact and near-duplicate detection with window functions. Bad rows go to a quarantine table tagged with one of 21 reason codes. Then a 23-expectation Great Expectations suite certifies what was published. Customer PII is encrypted per value with AES-256-GCM.

    • 21 reason codes
    • Great Expectations
    • Delta CHECK constraints
    • AES-256-GCM

    Gold · features without hindsight

    28 features that only know the past

    Velocity counts over 1-hour, 24-hour and 7-day windows, amount z-scores, implied travel speed between swipes, and new-device and new-merchant flags. Every window ends one second before the transaction. Merchant-category risk is fitted on the training months only, and merchant fraud rates only use reports filed before that day.

    • point-in-time windows
    • OPTIMIZE · ZORDER
    • data-quality marts

    Model · LightGBM + MLflow

    Train on the past, test on the future

    Train on January to April, tune the alert threshold on May, and evaluate once on June, never on a random shuffle. Class imbalance is handled with scale_pos_weight. MLflow logs every parameter, metric, plot and the exact Delta version of the features table, then registers the model under a champion alias.

    • time-based split
    • recall ≥ 95% target
    • model registry

    Score · batch inference

    Every transaction gets a score

    The champion model is loaded from the registry and applied across the whole table with Spark's mapInPandas, so it scales with the cluster. Out come alerts, daily KPIs, merchant risk and customer risk marts.

    • mapInPandas
    • fraud_alerts
    • merchant_risk

    Reconcile · ledger vs settlement

    Two passes, seven verdicts

    Pass one matches on the reference key. Pass two recovers settlements that lost their reference by matching auth code and merchant. Amounts within $0.05 and dates within two days count as matches. Every record ends up in one of seven categories, and the result is scored against injected ground truth.

    • two-pass matching
    • tolerance windows
    • CSV break report

    Serve · dashboards

    Small, safe extracts for humans

    Gold marts are exported as compact, aggregated, PII-checked Parquet files: about 110 KB for a seven-page Streamlit app, plus a star schema with DAX measures for Power BI. An export that contains an identifier fails the job.

    • Streamlit
    • Power BI
    • PII guard

      10 · How it came together

      Eleven phases. Five things went wrong.

      Each phase followed the same loop: build, verify at scale, commit, record the numbers. The detours taught the most.

      1. 00

        Scaffold

        uv, Makefile, Docker Compose, config profiles, a storage abstraction with one bucket per layer.

        Detour: MinIO's images and binaries were gone and its repo archived. Swapped in SeaweedFS. Because the code only speaks S3, nothing else changed.
      2. 01

        Simulator

        Dimensions, fraud episodes, defect injection, ledger and settlement with ground truth. Chunked to stay under 1 GB of RAM.

      3. 02

        Bronze

        Tokenize on landing, file tracking, Delta transaction IDs, corrupt-record capture. Verified that row counts match raw line counts.

      4. 03

        Silver

        Schemas, 21 reason codes, deduplication, quarantine, CHECK constraints, Great Expectations, AES-GCM.

        Detour: timestamps shifted by five hours. PySpark returns local-time datetimes, so the driver, JVM and Spark were all pinned to UTC.
      5. 04

        Gold

        28 point-in-time features, compacted with ZORDER, plus data-quality marts.

      6. 05

        Model

        LightGBM, time split, recall-targeted threshold, MLflow registry, batch scoring.

        Detour: PR-AUC 0.9994 was too easy, so the simulator was rebuilt with confounders. Also, a SQLAlchemy 2.1 release broke MLflow, fixed by pinning 2.0.
      7. 06

        Reconciliation

        Two-pass matching with tolerances, seven categories, accuracy against truth, and a runtime benchmark.

      8. 07

        Security & audit

        Encryption at rest, role-gated audited PII decryption, a time-travel replay command, Terraform for AWS.

        Detour: enabling bucket encryption made every write fail until a key-encryption key was configured. Caught immediately, then fixed properly.
      9. 08

        Orchestration

        Databricks Asset Bundle (serverless) and an equivalent Airflow DAG.

      10. 09

        Dashboards

        A seven-page Streamlit app and a Power BI star schema.

      11. 10

        CI & polish

        GitHub Actions passed on the first run. Docs and results are generated from the run's JSON.

      11 · Insights

      What this project taught me.

      i

      A suspiciously good metric is a bug report.

      A near-perfect score called for an investigation, not a résumé line. Fixing the data made the model worse, and made the result more honest.

      ii

      Idempotency needs two locks.

      A processed-file log alone fails if a job dies between two commits. Delta transaction IDs close that gap.

      iii

      Measure the claim, label the guess.

      Recon accuracy is checked against injected truth. The manual-time baseline is an assumption, so it's labelled as one.

      iv

      Abstractions pay rent.

      One storage interface turned a dead dependency into a config change, and lets the same code run on S3, R2 or Unity Catalog.

      v

      Time zones fail quietly.

      No error, just wrong hours. Pin UTC in every runtime, then derive local time on purpose.

      vi

      Where the model misses is the story.

      Velocity bursts on chip cards nearby, and late-night shoppers, overlap with real behaviour. That's where the next feature work goes.
